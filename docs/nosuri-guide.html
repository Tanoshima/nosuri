01nosuri とは

城跡、古墳、旧街道、地質露頭 — 数百年から数億年のスケールでそこに在り続けている場所を、位置と分類の両方から探せるようにするサービスです。まずは自分用として作り、いずれ一般公開することを想定しています。

誰のためのものか

「近くにある史跡を知りたい」「この時代の遺構だけ地図で見たい」という、現地を歩く人。専門家向けの学術データベースではなく、出かける前と歩いている最中に使う道具を目指します。

何ができるようになるか

現在地からの距離、カテゴリ（城跡→山城など）、タグ、時代 — これらを掛け合わせた横断検索と、その結果の地図表示。オープンデータを土台に、手作業の加筆で精度を上げていきます。

いまどの段階か

アプリケーションコードはまだ存在しません。scrap & build 期として、データ基盤（PostGIS）とオープンデータ取り込みスクリプトだけを作っています。抽象化は必要になってから入れる方針です。

設計方針：早すぎる構造化をしない。Python パッケージも Go モジュールも、それを正当化するだけのコード量が集まってから作ります。

03データ設計の原則

この 3 つが、以降のすべての実装判断の前提になります。

raw と main の二層構造

オープンデータは定期的に取り込み直します。そのとき手作業で加筆した内容を上書きしてしまわないよう、テーブルを 2 層に分けています。

Raw layer

raw テーブル

上流オープンデータの 1:1 ミラー。いつでも作り直してよい前提で、元レスポンスを jsonb のまま保持します。取り込みスクリプトが書き込むのはここだけです。

Main layer

main テーブル

アプリケーションが読む層。手作業の編集、複数ソースのマージ、raw 行への参照を持ちます。取り込みコードから直接書き込んではいけません。

raw → main への昇格は独立した関心事として扱い、まだ実装していません。現在存在するのは raw テーブル 2 本だけです。

空間データ

緯度経度は PostGIS の geometry(Point, 4326) として保存します。距離・範囲の判定はアプリ側で計算せず、ST_DWithin / ST_Distance など SQL の空間関数で表現してください。座標が取れなかった行は geom が NULL になります。

-- 例：ある地点から 5km 以内の史跡を近い順に
SELECT s.name, ST_Distance(a.geom::geography, p.geom::geography) AS m
FROM raw_jps_item_api a
JOIN raw_jps_shiseki s USING (subject_uri),
     (SELECT ST_SetSRID(ST_MakePoint(139.7671, 35.6812), 4326) AS geom) p
WHERE ST_DWithin(a.geom::geography, p.geom::geography, 5000)
ORDER BY m;

分類は 3 軸で直交させる

横断検索を成立させるため、分類軸は次の 3 つに固定します。新しい種類のデータを足すときも、4 つ目の軸を作らず既存の 3 軸に収めます。

カテゴリ（階層）

城跡 → 山城 のように親子関係を持つ分類。ものの種類を表します。

タグ（フラット）

階層に馴染まない特徴づけ。横断的な絞り込みに使います。

時代 / 年代

いつの遺構か。地質サイトでは地質年代が入ります。

04取り込みパイプライン

現在動いているのは Japan Search（JPS）からの取り込み 1 系統です。SPARQL で対象の一覧を取り、続いて item API を 1 件ずつ叩いて正確な座標や説明文を足す、2 段構えになっています。

Upstream jpsearch.go.jp/rdf/sparql type:史跡 などを 500 件ずつページング取得
Script ingest_jps_shiseki.py パース・subject 重複排除・500 件ごとに commit
Raw table raw_jps_shiseki 名称・時代・画像・出典。subject_uri で UPSERT
Upstream jpsearch.go.jp/api/item/{id} 1 件ずつ。既定 0.3 秒の間隔を空ける
Script ingest_jps_items.py 未取得の subject_uri を洗い出して補完
Raw table raw_jps_item_api 緯度経度（geometry）・説明・権利区分
Not built yet promotion job raw を突き合わせて main へ昇格させる処理
Not built yet main tables 手編集・カテゴリ・タグ・時代を持つ層
Not built yet Go API → React SPA 検索 API と地図 UI

再実行したときの振る舞い

  • どちらのスクリプトも subject_uri を主キーとした UPSERT なので、何度流しても行は増えません。上流で内容が変わっていれば上書きされ、fetched_at が更新されます。
  • SPARQL の OPTIONAL は同じ ?s を複数行返すことがあるため、ページ内とラン全体の両方で重複排除しています。
  • ingest_jps_items.py は既定で raw_jps_item_api に未登録の subject だけを対象にします。全件取り直すときは --refresh を付けます。
  • raw_jps_item_api.subject_uri は raw_jps_shiseki への外部キー（ON DELETE CASCADE）です。親を消せば子も消えます。

DDL は db/ 配下にあります。db/init.sql は拡張の有効化だけで、テーブルの作成は個別の SQL ファイルを psql $DATABASE_URL -f db/<file>.sql で適用します。

06開発環境の使い方

環境は devcontainer + Nix flake で完全に再現できます。VS Code で開いて Reopen in Container を選ぶだけです（CLI 派は devcontainer up --workspace-folder .）。初回はイメージ取得と Nix のビルドで 10〜20 分かかります。

  • direnv（nix-direnv）がプロジェクトルートへの cd で dev shell を自動有効化します。.envrc is blocked と言われたら direnv allow。
  • PostgreSQL は自動起動しませんが、コンテナ起動時に pg-up がバックグラウンドで走ります（ログは /tmp/pg.log）。
  • Python の venv（ingest/.venv/）は shell 入室時の uv sync で同期済みです。

接続情報

DATABASE_URL と PG* は flake の shellHook が自動で export します。.env ファイルは不要です。

変数値
DATABASE_URLpostgresql://127.0.0.1:5432/nosuri
PGHOST / PGPORT127.0.0.1 / 5432
PGDATABASE / PGUSERnosuri / postgres（パスワードなし・trust 認証）
PGDATA$PWD/.local/state/postgres

ホスト側の GUI クライアント（DBeaver / TablePlus など）からは、ポート転送済みの localhost:5432 に同じ情報で接続できます。コンテナ内なら VS Code の SQLTools が同梱済みです。

よく使うコマンド

pg-up                              # PostgreSQL 起動（初回は initdb + DB 作成 + init.sql）
pg-down                            # 停止
psql $DATABASE_URL                 # 接続
devcontainer-exec                  # ホストからコンテナの zsh に入る

cd ingest
uv add <package>                   # 依存追加（pyproject.toml と uv.lock を更新）
uv run pytest                      # テスト実行
uv run python scripts/<file>.py    # スクリプト実行
venv を直接 pip で触らないこと。依存は必ず ingest/ で uv 経由。CLI ツールや PostgreSQL 拡張を増やすときは flake.nix を編集します。

07スクリプトの実行

どちらも ingest/ 配下で uv run python scripts/… として起動します。DATABASE_URL が未設定だと（dry-run を除き）終了コード 2 で止まります。

ingest_jps_shiseki.py — 一覧の取り込み

uv run python scripts/ingest_jps_shiseki.py              # 既定の 4 type を全件
uv run python scripts/ingest_jps_shiseki.py --limit 20    # 動作確認
uv run python scripts/ingest_jps_shiseki.py --types 史跡 名勝
uv run python scripts/ingest_jps_shiseki.py --dry-run     # DB に書かない
オプション既定値意味
--types史跡 / 史跡名勝天然記念物等 / 名勝 / 天然記念物取り込む JPS type
--limitなしtype ごとの取得上限（スモークテスト用）
--page-size500SPARQL の LIMIT
--sleep1.0ページ取得間の待機秒数
--dry-runoff取得とパースのみ。DB 接続もしない

ingest_jps_items.py — 座標と本文の補完

uv run python scripts/ingest_jps_items.py                 # 未取得ぶんすべて
uv run python scripts/ingest_jps_items.py --limit 10      # 動作確認
uv run python scripts/ingest_jps_items.py --refresh       # 取得済みも取り直す
uv run python scripts/ingest_jps_items.py --sleep 0.2
オプション既定値意味
--limitなし処理する subject 数の上限
--sleep0.3API 呼び出し間隔。上流に負荷をかけない
--refreshoff取得済みの subject も対象にする
--commit-every200この件数ごとに commit

1 件ずつ HTTP を叩くうえ既定で 0.3 秒待つため、全件補完は数時間規模になります。進捗は 200 件ごとに fetched / with_coords / errors がログに出ます。404 と通信失敗はスキップして続行し、件数だけ数えます。

09運用とトラブル対応

データはどこにあり、いつ消えるか

実体は $PWD/.local/state/postgres（ワークスペースのバインドマウント上）です。pg-down／コンテナ再起動／Rebuild Container では消えません。消えるのは rm -rf .local/state/postgres、プロジェクトごと削除、別マシンへの移動です。.local/ は gitignore 済みなので、残したいなら明示的にダンプを取ります。

  • raw テーブル — バックアップ不要。取り込みが冪等なので、失ったら取り直す。
  • main テーブル — 手編集を含むので pg_dump で保存する。
mkdir -p backups
pg_dump -Fc $DATABASE_URL -f backups/nosuri_$(date +%Y%m%d_%H%M%S).dump
pg_restore -d $DATABASE_URL --clean --if-exists backups/nosuri_xxx.dump

backups/ を作ったら .gitignore に追加してください。

スキーマを変えたとき

db/init.sql は DB 新規作成時に一度しか走りません。既存 DB に反映するには次のどちらかを取ります。

# A. 手で当てる（データを残す）
psql $DATABASE_URL -f db/init.sql

# B. cluster ごと作り直す（データは破棄）
pg-down && rm -rf .local/state/postgres && pg-up

SQL ファイルが増えてきたら db/migrations/ 構成への移行を検討します。

詰まったとき

PostgreSQL に接続できない
tail -50 /tmp/pg.log

ポート競合かデータ破損が主因。復旧しなければ cluster をリセットします。

direnv: error .envrc is blocked
direnv allow

flake.nix を編集すると再許可が必要になることがあります。

flake が "not tracked by Git" と言う

新規ファイルが未 stage のときに出ます。git add flake.nix で解決（commit は不要）。

コンテナを作り直したい

VS Code: コマンドパレット → Dev Containers: Rebuild Container Without Cache／CLI: devcontainer up --workspace-folder . --remove-existing-container

セキュリティ：ローカルの cluster は listen_addresses = '127.0.0.1' かつ trust 認証です。この設定を本番や共有環境に持ち込まないこと。
